

ODEON — PORTFOLIO ENTRY (ENGINEERING DIARY)
1. System Overview

ODEON is an active, early-stage (≈ first development phase) distributed simulation platform built as a schema-driven web system on top of the WebBox infrastructure layer.

It is structurally derived from a prior “planning-style” application model but has been re-implemented to operate on a modernized, framework-driven internal platform (WebBox in REST execution mode).

The system is designed as a three-tier computational pipeline with strict separation of responsibilities across UI, backend, and simulation execution.

2. Runtime Architecture

ODEON is composed of three primary application layers and supporting infrastructure services:

Core Application Services
SvelteKit BFF (Frontend / Edge Controller)
Serves UI and handles all browser interactions
Acts as the only public entry point to the system
Performs request validation and session mediation
NestJS Core API
Central domain logic layer
Handles data orchestration, persistence logic, and business rules
Exposed only internally through the BFF layer (not publicly accessible)
Python Flask Solver (Algorithmic Engine)
Dedicated computational engine for scenario execution
Processes simulation workloads and returns structured results
Operates independently from UI and API layers
Infrastructure Services
PostgreSQL
Primary persistence layer for system state and simulation data
Accessed exclusively via NestJS Core API through Prisma ORM
Redis
Session cache and transient state storage
Stores authenticated user profiles and access context
Keycloak (Remote Identity Provider)
External authentication authority
Provides SSO-based identity verification
Integrated via token validation and session mapping at the BFF layer
3. Data Boundaries

ODEON enforces a hybrid data model depending on deployment context:

On-premises deployments: isolated PostgreSQL instance per installation
Multi-tenant environments: shared database with strict row-level isolation via org_id

All data access is enforced through backend-level context injection, ensuring that:

no raw client queries reach the database
all queries are scoped to authenticated organizational context
4. Authentication Architecture
Authentication is fully federated via Keycloak SSO
No local credential store exists inside application services
SvelteKit BFF intercepts authentication tokens and:
validates token integrity
maps identity into Redis session cache
issues a single hashed session cookie to the client

Session state is therefore:

server-mediated, cached, and non-exposed to the browser as raw identity data

5. Communication Model

The system follows a strict layered communication graph:

Browser → SvelteKit BFF (HTTP)
SvelteKit BFF → NestJS Core API (internal REST over Docker network, signed requests)
NestJS Core API → PostgreSQL (Prisma ORM)
SvelteKit / NestJS → Flask Solver (HTTP simulation dispatch)
SvelteKit ↔ Redis (session retrieval and caching)
BFF ↔ Keycloak (authentication validation flow)

No direct browser-to-backend or browser-to-database communication exists.

6. Execution Lifecycle Model

ODEON implements a controlled simulation lifecycle:

Input construction (UI-driven schema forms)
Validation (schema + backend validation layers)
Request orchestration (BFF → Core API)
Data persistence (NestJS → PostgreSQL)
Simulation execution (Flask Solver)
Result retrieval and UI rendering

The solver stage is the final computational boundary of the system.

7. WebBox Dependency Layer

ODEON is built on top of the WebBox infrastructure layer operating in REST execution mode, which provides:

schema-based system definitions
reusable controller/service abstractions
structured API generation patterns
shared validation and form modeling primitives

Within ODEON, WebBox acts as the system construction substrate, not merely a library dependency.

8. Reusable Engineering Components
BaseRestController
Generic CRUD abstraction for NestJS APIs
BaseService (Prisma Wrapper)
Standardized data access layer with dynamic model binding
FORM-CTX
Reactive schema-driven form system in SvelteKit
VALIDATION-SERVICE
Runtime schema validation engine with instance-scoped execution
Parse-Org-Pipe
Global request interceptor enforcing tenant-level data isolation
Prisma-to-Scheme Parser
Generates schema definitions from Prisma models for frontend/backend synchronization
9. Infrastructure Characteristics
Fully containerized deployment via Docker Compose
Multi-service orchestration (UI, API, solver, DB, cache, auth)
On-premises deployment compatibility (utility environments)
Optional cloud registry distribution for prebuilt images
Strict separation between build-time and runtime configuration injection
10. Non-Obvious System Properties
The frontend (SvelteKit) functions as a security and routing enforcement layer, not just a UI renderer
Backend services are intentionally inaccessible from external networks
All tenant isolation is enforced at backend query construction level via request-context injection
Schema definitions act as a unified contract for UI generation, validation, and database access
The solver acts as a fully decoupled computational subsystem with no dependency on UI state
Summary

ODEON is a schema-driven distributed simulation system where:

UI, API, and computation layers are strictly separated
authentication is fully federated and session-mediated
data access is context-isolated at backend level
system behavior is largely derived from reusable schema and controller abstractions
WebBox functions as the underlying structural platform enabling system generation
